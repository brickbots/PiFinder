# PiFinder v2.6.3 Release Notes

**There was no public 2.6.2.** A 2.6.2 build was cut to the release branch for internal use, with no announcement and no notes, and its update offer was withdrawn when it emerged that some rev4 units — the ones that shipped with a 12 mm lens and nothing in their configuration saying so — would stop solving on update. That regression is fixed in this release (see "Your PiFinder Now Works Out Its Own Lens"), and 2.6.3 supersedes 2.6.2 entirely: whether your device runs 2.6.1 or briefly took 2.6.2, it updates straight to 2.6.3. These notes cover everything since 2.6.1, with the internal 2.6.2's changes folded in.

PiFinder now understands that field of view is a property of the **sensor and the lens together**, which is what lets you fit a different lens and have the solver, the SQM and the chart all follow — and where nobody has stated which lens is fitted, the device now measures it for itself. The Focus screen stops fighting you by holding the exposure still while you turn the lens. **Nearby** now measures distance on the sky rather than on a swapped sphere, so the objects it ranks and the markers the chart draws are the ones actually near where you point. **Stellarium** can now push targets to the PiFinder the way SkySafari always could. The chart names the object at its center, the STATUS screen shows whether the GPS is actually talking, and the web interface's equipment and GPS forms now say so when they cannot read what you typed instead of pretending they saved it. All of this sits on top of the largest documentation pass the project has had: the manual rewritten end to end into a plain, translatable style, with a new Sky Quality Meter page and a batch of factual corrections driven by real support questions.

If you are on 2.6.1 and you have not changed your lens, this release changes nothing about what your device reads or how it solves. Update freely. If your PiFinder shipped with a 12 mm lens, it now works that out for itself rather than assuming the 16 mm.

## ⚠️ After You Update

- **A new `Settings → Advanced → Lens` setting appears, already set correctly.** An install with no stored lens resolves to the lens that ships with your sensor (HQ → 25 mm, imx296 / imx462 / imx290 → 16 mm). This reproduces the field widths previously stored as per-sensor constants to within 0.03°, which is under 0.01 mag of SQM — **no existing user's reading moves and no plate solve behaves differently.** You only need to touch this setting if the lens on the front of your PiFinder is not the one it shipped with.
- **If your PiFinder shipped with a 12 mm lens, it fixes itself on the first clear night.** Some rev4 units left with the 12 mm rather than the 16 mm and nothing in their configuration said so. Set the Lens if you like, but you do not have to: the PiFinder allows for every lens it could have shipped with until it has measured which one it has, then writes that lens down. It takes three solves. See "Your PiFinder now works out its own lens" below.
- **State the lens you actually have.** The lens cannot be detected, only declared, and the solver's search window is now centred on what you declared. Naming the wrong lens stops solving **completely** rather than degrading it — and because auto-exposure steers on match count, it presents as an exposure problem, not a configuration one. The focal length is marked on the lens barrel. See "Known sharp edges" below.
- **On the Focus screen, UP and DOWN now change the exposure**, and a new bar along the bottom of the screen shows the held exposure and the keys that change it. UP and DOWN were previously no-ops there. `+` and `-` are unchanged and still control magnification. Nothing you do on this screen is saved — the exposure is held for the visit and handed back when you leave, and `Camera Exp` in the menu still reads whatever you last saved. The Stats view reports the regime as `HOLD` while you are on the screen.
- **The Focus screen's Quick Menu no longer offers Exposure** (#620). UP and DOWN do that job directly now. To set an exposure the PiFinder keeps, go to `Settings → Camera Exp` as usual. Press and hold SQUARE on the Focus screen and you get HELP.
- **The Nearby sort ranks by true angular distance now, so the order you see changes.** The old ranking measured separation on a sphere with its axes swapped. It was right only for objects sharing a meridian, and got worse the further from the celestial equator you pointed. The chart's nearby-DSO markers ran on the same index and get the same fix.
- **A Nearby list now holds the 200 nearest objects rather than the whole catalog**, which is what keeps the re-rank off the frame budget while you slew. An object on the far side of the sky is no longer reachable by scrolling down a Nearby list. Catalog and RA sorts still expose every object.
- **In the Nearby sort, the top row follows your pointing.** While the cursor sits on the first row a re-rank leaves it there, so the focused object stays whatever is nearest. Once you scroll down, the cursor pins to the object you selected and follows it through the ranking instead; scrolling back to the top re-arms the tracking.
- **Object Details opens faster if you have a long observing log**, and the remote web interface's object-details view now works for objects opened from a Nearby-sorted list. It was silently blank on that path.
- **If you run an alt-az telescope on an equatorial tracking platform, set Mount Type to Alt-Az, not Equatorial.** The manual previously said the opposite. That misconfiguration is exactly what makes Push-To corrections jump around. This is a documentation correction, not a code change — but if you configured your device by following the old text, change it.
- **A rev4 board takes Camera Type `v3 - imx462`.** Also a documentation correction; the manual did not say so before, and rev4's card slot is externally accessible so people hit this during setup.
- **The chart gains a readout naming the object at its center, and it is on by default.** A line along the bottom of the chart names the drawn marker nearest the middle, and RIGHT opens that object's details. Turn it off at `Settings → Chart → Center Object` if you want your chart exactly as it was.
- **The STATUS screen gains a `GPS MSG` row** showing the last message the GPS receiver sent and how long ago it arrived. On a healthy unit the name churns and the age sits near zero; a frozen name with a climbing age means the link is dead. You do not need to do anything with it — it exists so support threads can tell four kinds of GPS failure apart.
- **Stellarium can now push targets to the PiFinder.** Same LX200 protocol, same port 4030 SkySafari uses; add a Meade LX200 compatible telescope in Stellarium pointed at `pifinder.local`. SkySafari setups are unchanged.
- **The web interface's equipment and GPS forms now reject input they cannot read, and say so.** Before, an unparseable value — a decimal comma is the easiest trigger — either reported "Eyepiece added" while saving nothing or returned a raw server error. Failures now re-render the form with a message and the values you typed. Fractional measurements like a 279.4 mm aperture are now accepted and survive a reload.
- No migration runs on update. The one thing that does write to your configuration file is lens self-heal, and only on a device that has never had a lens stated: after three agreeing solves it records the lens it measured, under `camera_lens`. It writes nothing else, and nothing at all if you have set the lens yourself.

## New Features

### Lens Selection and a Derived Field of View (#608, #609)

Field of view used to be three hard-coded constants that disagreed with each other and with the hardware:

| Consumer | Constant | Correct for |
|---|---|---|
| solver | `fov_estimate=12.0`, `fov_max_error=4.0` | 3 of the 4 sensor × lens combinations we can ship |
| SQM | `radiometric_fov_degrees`, per sensor | the 16 mm only |
| chart frustum | `9.5` | nothing currently shipped |

Nothing in the code said which lens any of them assumed. The practical consequence: a 12 mm lens on an imx296 images 16.38°, which falls outside the solver's `[8.0, 16.0]` window. Tetra3 enforces that window twice — pruning candidates before verification and rejecting survivors after fitting — so such a frame **does not solve at all**, however many good stars it contains.

All three now derive from one place, `PiFinder.optics`, which models the **optical train**: a camera profile paired with the lens fitted in front of it.

- **`Settings → Advanced → Lens`**, beside Camera Type, offering 12 mm, 16 mm and 25 mm. The menu shows the lens actually in force rather than the first entry in the list, including on installs that have never stored the setting.
- **Changing the lens restarts the PiFinder.** Everything that reads the lens live would follow it on the very next frame — the FOV gate, SQM's radiometric field width and the chart's frustum shading all re-resolve per frame. Tetra3's internal pattern cache would not: it stores results already filtered against whichever search window was in force when they were computed, under a key that does not mention the window, and nothing ever clears it. So a lens change could leave the solver holding stale work and appear not to have taken. Restarting is the reliable fix for a setting you change about once in the life of the device.
- **The gate is ±15% of the derived field of view**, proportional rather than a fixed number of degrees, which is *tighter* than the old fixed pair (effectively ±33%) while being correct for every combination rather than three of four.
- **Effective, not nominal, focal length drives the arithmetic.** The shipped "16 mm" measures 15.61 mm, and that single value reproduces both independently calibrated SQM field widths (imx296 13.71°, imx462 10.38°) to within 0.02°. Two different sensors agreeing on one lens is what makes it a measurement rather than a fudge factor. Deriving from the nominal 16.0 would have shifted every existing user's SQM by ~0.05 mag. The 12 mm has since been measured the same way and comes out at **13.04 mm** — 8.7% *long*, where the 16 mm runs 2.4% short, so no label predicts its own glass. The menu still shows the number printed on the barrel.

The field of view each combination now derives:

| Sensor | 12 mm | 16 mm | 25 mm |
|---|---|---|---|
| imx296 | 16.38° | **13.71°** | 8.26° ✗ |
| imx462 / imx290 | 12.44° | **10.40°** | 6.26° ✗ |
| HQ (imx477) | 20.43° | 17.12° | **10.33°** |

Bold is the lens that ships with that sensor and the value used when no lens is stated. ✗ marks combinations the shipped pattern database cannot solve — see "Known sharp edges".

### Your PiFinder Now Works Out Its Own Lens (ADR 0029)

The lens setting above has a gap in it, and it is one we put there. Deriving the search window from the lens is only right when we *know* the lens — and for an install that has never stored one, the "16 mm" the code fell back to was never knowledge. It was a guess wearing knowledge's confidence.

That guess is wrong on real hardware. Some rev4 units shipped with a 12 mm lens and nothing in their configuration recording it, so on 2.6.2 they searched a window centred on 10.40° for frames that are actually 12.44° wide. **Those units stopped solving on update having changed nothing.** The configuration that broke them is the configuration we shipped them.

The fix is to make the search window's width follow how much the PiFinder actually knows:

- **You stated the lens** (from the menu, or because the device measured it) → the window stays ±15% of that one lens's field of view, exactly as 2.6.2 already did. Nothing changes for you.
- **Nobody has stated it** → the window covers *every* lens that sensor has shipped with, so the device solves on either one while it works out which it has.

| Sensor | Lenses it shipped with | Window when the lens is unstated |
|---|---|---|
| imx462 / imx290 | 12 mm (12.44°), 16 mm (10.40°) | `11.57 ± 2.73` = [8.84, 14.30] |
| imx296 | 12 mm (16.38°), 16 mm (13.71°) | `15.25 ± 3.59` = [11.65, 18.84] |
| HQ (imx477) | 25 mm (10.33°) | [8.78, 11.88] — **unchanged** |

The imx462's window sits comfortably inside the fixed `[8.0, 16.0]` that 2.6.1 used, which is the behaviour these units are known to work under. The HQ only ever shipped one lens, so nothing about it widens at all.

**Then the PiFinder identifies the lens for itself.** A successful solve reports the field of view it measured, and the sensor is already known, so what is left is the lens. After **three consecutive solves agreeing to within 5%**, the device writes that lens into the Lens setting and narrows its window onto it. From then on the menu shows the real lens and the solver has 2.6.2's full precision back.

**The 12 mm's focal length had to be measured before any of that could work** (#627, #628). The registry carried the lens's nominal 12.0 mm, which derives a 13.51° field against a real 12.4366 ± 0.0025° — 7.9% out, and self-heal identifies a lens only within 5%. So a 12 mm unit fitted a field that matched no lens in the registry, on every frame, and took the branch above for third-party glass: write nothing, keep the wide window. The units this release exists to fix would have solved but never promoted. At the measured 13.04 mm that error is −0.07%, and promotion in three solves is demonstrated on the board that surfaced the bug, in both directions. It also corrects something nobody was looking for: SQM on a 12 mm unit was integrating over a field 8.6% too wide, and carrying the 16 mm's zero point across.

Four things it deliberately will not do:

- **It never overwrites a lens you set.** Your claim stays authoritative even when the measurement disagrees, because quietly overruling the setting would make the menu a lie. A mis-stated lens still means no solves, exactly as 2.6.2 documented.
- **It writes nothing when the measurement matches no lens we sell.** Third-party glass keeps the wide window and approximate SQM forever, which is honest: we do not know its focal length. A wrong write would be worse than none, because the window then tightens around it and the device can no longer measure its way out.
- **It never drops the window entirely.** Widening costs nothing measurable in solve time (1.1–1.4 ms at every width tested, against 1.5 ms with no window at all), but the *upper* bound is load-bearing: with injected noise, hintless searches returned confident false solves at 20–23° that the match threshold did not reject. The window is what catches those, so it stays finite.
- **It writes at most once per device.** The write is what ends the condition that triggers it.

Why widen rather than tighten the tolerance everywhere? Because the two failures are not the same size. A frame *outside* the window burns the entire solve timeout and returns nothing, every frame, forever. Against a wider window's ~0.3 ms, an over-tight one is the expensive mistake by three orders of magnitude.

No migration runs, and no rev4 unit is assumed to have a 12 mm. Not all of them do — a migration keyed on the board would have fixed most units by breaking the rest, and broken them in exactly the way this release exists to fix. The reasoning is in `docs/adr/0029-fov-gate-width-follows-lens-confidence.md`.

### The Focus Screen Holds the Exposure (#614, #620)

You open the Focus screen *because* focus is bad. But bad focus is what starves the plate solver of matches, and solver-driven auto-exposure steers on that match count — so the controller kept adjusting underneath you, and once matches hit zero, zero-match recovery walked the exposure much further still. The HFD readout moved and the visible stars changed for reasons that had nothing to do with the lens you had just turned. The signal you were trying to judge shifted under you.

The Focus screen now takes the exposure for the duration of the visit and hands it back on exit.

- **Entering** freezes whatever exposure is already in effect, without snapping to a menu value — under Auto it holds wherever the controller had settled, including off-ladder values like 0.32044 s.
- **UP** lengthens and **DOWN** shortens the exposure, stepping along the Camera Exp menu's own rungs (0.025 s … 1 s). The ends of the ladder hold rather than wrap. `+` and `-` remain magnification.
- **Leaving** restores the previous regime — back to Auto if that is where you were.
- **Nothing is persisted.** The hold never writes `camera_exp`. To save a value, use `Settings → Camera Exp`.
- **A standing bar along the bottom** carries the held exposure on the left and the keys on the right, so the exposure is readable for as long as you are on the screen rather than flashing and vanishing. The Image view lists the exposure keys only, since `+` and `-` do nothing there, and the Stats view has no bar because it already reports the exposure and its `HOLD` regime in full. The bar's rows are reserved out of the camera area rather than drawn over it, so no raw sensor pixel is hidden behind it.

This is the other half of a boundary the codebase already described: zero-match recovery is explicitly not responsible for defocus, because the focus indicator owns that. Now the focus indicator's screen suspends recovery too.

### Stellarium Can Push Targets (#621)

Stellarium — including Stellarium Mobile Plus — now connects to the PiFinder the same way SkySafari does and can send an object to the observing list for Push-To guidance. Same LX200 protocol, same port 4030: in Stellarium's telescope settings, add a **Meade LX200 compatible** telescope at `pifinder.local` (or the numeric IP from the STATUS screen). Stellarium marks the telescope's position on its chart, and a selected object sent to the PiFinder lands in the observing list exactly as a SkySafari push does. Stellarium also sends its own observing site and clock while connecting; the PiFinder accepts them and keeps using its own GPS position and time.

Getting there meant fixing the position server's LX200 dialect, because several replies were wrong in ways that only a second client ever exposed:

- **Degrees-to-arcminutes conversion multiplied the fractional digits by 60 and truncated**, which is only right when the product happens to be four digits — 42.10° answered an out-of-range `42*60` and 42.05° answered `42*30` for a true 3.0′. Roughly one site in six was silently wrong. Replaced with divmod arithmetic that rounds and carries.
- **Longitude dropped its sign**, so Berlin (13.4° E) read as 13.4° West. `:Gg#` now uses Meade's documented positive-west 000–359 convention — the same one `:Sg#` accepts — with the wrap applied after rounding so a site just east of Greenwich cannot land on `360*00`.
- **The UTC-offset reply parsed `"-0500"` as −500 hours**, a 20-day timedelta, masked only because the shared clock is always UTC-aware. `:GL#` and `:GC#` now report local time and `:GG#` returns LX200's sign-inverted `sHH` form (US Eastern is `+05`, not `-05`). Locale-dependent date formats are hardcoded to what LX200 specifies.
- **A packet carrying two commands only dispatched the first**, so Stellarium's goto — which sends `#:Sr…##:Sd…#` in one write — silently never fired. Reads are now split into `#`-framed commands and each is dispatched, with the leading `#` optional so unprefixed SkySafari traffic parses through the same path.

SkySafari is deliberately protected from all of this: `:Q#` is answered only for a client that identified itself with Stellarium's ACK (an unsolicited reply can desync SkySafari's parser), per-connection state is reset so a SkySafari session cannot inherit a stale Stellarium site, and a pushed object is no longer labelled as coming from SkySafari when Stellarium may have sent it. The position server also gains its first test suite — 382 lines covering both dialects.

### The Chart Names What You Are Centered On (#633, ADR 0031)

A new readout along the bottom of the chart names the **center object** — the drawn marker nearest the middle of the chart — as its designator plus the first other name the catalogs carry, marquee-scrolled when it does not fit, with an arrow glyph advertising that RIGHT opens that object's details. The choice is held sticky between solves so it does not alternate between two near-equidistant markers as the pointing drifts.

The candidate set is exactly what the chart drew this solve, restricted to the screen bounds, so the readout never names something you cannot see — that rather than the Nearby ranking, and distance measured in screen pixels, is the decision ADR 0031 records. The readout repaints its strip from a cached copy of the chart backdrop every frame, so the marquee scrolls smoothly at display rate rather than stuttering at the 1–2 Hz solve rate, and the projection of the candidate set is batched into a single skyfield round trip (3.68 ms → 0.18 ms per solve, bit-identical output).

`Settings → Chart → Center Object` (Off/On, **default On**) controls it, and RIGHT is gated on the same switch — off, blank, or no solve leaves RIGHT inert exactly as before. The chart also gains `serialize_ui_state`, so `/api/current-selection` now reports the center object and the readout state to the web interface.

### The STATUS Screen Shows GPS Link Health (#635, ADR 0032)

One new row — `GPS MSG TIMEGPS 0.4s` — showing the last event the GPS process handled and how long ago the main process received it. That single row discriminates four failure modes that previously all looked identical from anywhere above the parser:

| What you see | What it means |
|---|---|
| name churning, age near zero | healthy — the receiver is talking and being understood |
| `?0135`-style marker | the receiver is talking a dialect the parser does not decode |
| `?CKSUM` | bytes are arriving corrupted |
| name frozen, age climbing | the link is dead |

The parser change behind it is ADR 0032: a UBX frame that cannot be decoded now yields a marker instead of being silently dropped, which is what makes "we cannot read this" distinguishable from "nothing is arriving". All three GPS backends (UBX, GPSD, fake) publish through the same rate-capped channel — 20 Hz, a cap on reporting rather than parsing, so a resync storm cannot flood the queue.

One subtlety worth recording: the age is stamped by the **main process when it drains the queue**, not by the GPS process when it sends. `time.monotonic()`'s reference point is undefined across processes — on macOS it is process start — so stamping at the sending end made the row read a steady ~4 s stale against a fake GPS publishing every 0.5 s. Only the event name crosses the process boundary.

## Fixes

### Nearby Ranks by True Angular Distance, in a Bounded Window (#622, ADR 0030)

Two features ask the same question — which catalog objects are near where the scope points? The object list's **Nearby** sort wants them ranked nearest first; the chart's nearby-DSO marker layer wants everything inside the current field. Both are served by one `BallTree` with scikit-learn's `haversine` metric, and that metric reads **dimension 0 as latitude**. Declination is the latitude. The tree was built and queried as `[ra, dec]`.

With the axes swapped, separations came out right only between objects sharing a meridian, and worse the further from the celestial equator you pointed.

The mistake hides, which is why it survived. When two objects share an RA the metric degenerates to `|dec1 − dec2|`, which is correct whichever way round the axes go — so any spot-check that holds RA fixed passes on a swapped index. Index and query are now `[dec, ra]`, and the tests place objects off a shared meridian and at high declination, where a swapped axis order is loudest.

The chart layer gains more from this than the list does. A mis-ranked list is something you might notice; a marker silently absent from the field is not.

**Ranking is now bounded.** Ordering the whole catalog to draw about nine rows cost O(N) twice over — once in the k-NN query, and again in the pure-Python cursor-tracking helper that rebuilds a lookup over the new ordering — on every re-rank, on the draw path, while you slew:

| Objects | rank everything | rank 200 | cursor helper |
|---|---|---|---|
| 14 000 | 1.5 ms | 0.09 ms | 7.6 ms |
| 40 000 | 4.4 ms | 0.13 ms | 22 ms |

(Measured on a fast dev machine; a Pi is roughly an order of magnitude slower, against a 33 ms frame budget.)

`NEAREST_LIST_CAP = 200` bounds both, and everything downstream with them. The cost is the one behaviour a user may experience as a loss: a Nearby list no longer scrolls down to the object 140° away. That object is not "nearby" under any reading, and paying O(N) on every degree of slew to keep the tail reachable is the wrong bargain.

**Staleness is measured on the sky, not per axis.** The re-rank used to trigger on raw RA/Dec degrees. One degree of RA spans `cos(dec)` degrees on the sky — 0.017° at Dec 89° — so that test re-ranked for movement you cannot see, exactly where slewing is slowest and a stall is most visible. And RA wraps, so the step from 359.5° to 0.5° read as 359 and fired continuously in a band around the meridian. Neither failure loses a refresh, so neither showed up as wrong output; both were pure cost. The trigger is now a great-circle separation against 1.0 true degree, at the cost of one `arccos`. The unconditional time-based refresh moves from 2 s to 10 s: its job is catalog and filter changes, not pointing, and 10 s bounds sidereal drift to ~0.04°.

**The carousel counts the list it actually navigates.** `UIObjectList` draws, scrolls, opens and serialises the *sorted* list, which is shorter than the source whenever the sort caps or deduplicates listings sharing an `object_id` — but it counted the source. Long-DOWN therefore parked the cursor past the end of the ranked window, and opening that row raised `IndexError`. The catalog's own object count is a different quantity and stays the source length, reported in the header where you are being told how big the catalog is.

Fixed alongside, all latent and adjacent:

- **A Nearby-sorted list blanked the remote web interface's object-details view.** The list arrives as the NumPy object array the ranking returns, and `serialize_ui_state` tested it for truthiness — which raises on a multi-element array. The raise landed inside the method's own `except`, so it never surfaced as a crash. It just serialised every object opened from a Nearby list as an error instead of state.
- The **"No Solve Yet"** message was unreachable and now appears.
- The **scrollbar** tolerates an empty list, which a sort can now legitimately produce from a non-empty source.
- The **spatial index** is cached on the catalog filter's `dirty_time`, the same key `UIChart` already used for its own nearby-marker index — so a filter edit cannot leave the list and the chart disagreeing about what is on the sky.
- The in-frame re-rank **holds off until the index is built**, rather than replacing a populated list with an empty one mid-draw.

The reasoning is in `docs/adr/0030-nearby-ranking-correctness-and-cost.md`.

### Opening Object Details No Longer Rebuilds the Observed-Objects Cache (#623)

Since #528 the observed-objects cache resolves every logged listing to its sky object id, so that logging an object marks it observed under all of its catalog names. It did that one lookup per listing — and `UIObjectDetails` built a new `ObservationsDatabase`, and therefore a new cache, on every entry into the screen. #564's index on `catalog_objects` took each lookup from a ~151k-row scan down to an index probe, which removed the stall; what remained was a per-entry cost that still grew with the size of your observing log.

The mapping is now one chunked query, and the screen shares a single `ObservationsDatabase` for the life of the UI process, exactly as it already did for the catalog handle. Opening the screen no longer rebuilds the cache at all.

Measured on a Pi 4 with 138 logged listings, against the indexed catalog DB: 7.2 ms of per-listing lookups versus 1.6 ms for the bulk query. Against an unindexed catalog DB — one built before #564, before the on-open backfill runs — 5.5 s versus 0.075 s.

The bulk query groups by catalog code rather than asking for a `(catalog_code, sequence) IN (VALUES …)` row-value match, and that detail is load-bearing. SQLite will not drive a two-column index from a row-value list: it constrains on `catalog_code` alone and scans the remainder of every catalog named in the chunk. WDS holds ~131k of the ~151k rows in `catalog_objects`, so a single logged double star pulled the whole WDS range into every chunk — 110 Messier listings plus one WDS listing measured 21.83 ms against 0.67 ms of per-listing lookups, a regression on the exact path the change set out to speed up. Grouped by catalog code, SQLite plans a probe per listing. There are 21 catalog codes, so this stays a handful of queries however large the log grows: 0.12 ms for that case, and 3.16 ms for 2 000 random listings against 14.07 ms of individual lookups.

### The Web Forms Validate at the API, Not Just the Browser (#571, ADR 0033)

The equipment handlers parsed form input with bare `float()`/`int()` inside a catch-all that logged and then rendered the success template regardless — so an unreadable value reported **"Eyepiece added, restart your PiFinder to use"** while saving nothing. The GPS form had no handler at all, so the same input reached you as a raw 500. A decimal comma is the easiest trigger, and PiFinder ships in German, Spanish, French and Chinese — but any unparseable value did it, including the blank instrument name of #569.

Field rules now live in one table beside the equipment dataclasses: the edit forms render them into their client-side check, and the API re-checks them before anything reaches your configuration. A failure re-renders the form with a message and the values you typed, in your language — 18 new translated strings across all four catalogs. Along the way:

- **Measurements are floats throughout**, so a 279.4 mm aperture is enterable and a configuration already carrying one now loads instead of aborting startup before the UI comes up (#291). Whole millimetres still display as `1000`, not `1000.0`.
- **The GPS form parses everything before locking anything**, so a bad clock entry can no longer half-apply a position. It also gains the decimal-comma normalisation the location forms got in #536, which never reached it, and two decimal→DMS bypasses in the locations page are closed.
- **The DeepskyLog import skips records it cannot read** — and says how many — rather than writing them through into your equipment list.
- **Route indexes are range-checked**, so a stale edit link renders an error page instead of a 500.

Covered by 68 new request-level tests, because the Selenium suite runs `en-US` and structurally cannot catch a decimal-comma bug. The rules themselves are recorded in ADR 0033 (equipment measurements are validated floats).

### Debug Frames Are No Longer Judged by Your Lens (#632)

`--camera debug` stopped solving for any developer with a stated lens. The debug camera declares the sensor its archived frames were shot on (`hq`), but the lens half of the optical train reads live from your configuration — so stating a 16 mm paired `hq × 16mm` (17.12°) against frames that are 10.2° wide, and tetra3 rejected every one before verification. Same shape as the rev4 regression, mirrored: there an assumption wore a statement's confidence; here a statement was made about hardware that is not in the loop.

The fix names the state rather than special-casing the debug camera. An **unknown optical train** is one whose frames did not come through this device's optics, and it extends ADR 0029's confidence ladder a third rung: stated → ±15%, assumed → union over shipped lenses, **unknown → no gate at all**. Two consequences follow from one rule: nothing about the device may be asserted about the frames (no FOV hint), and nothing about the device may be inferred from them (**no lens self-heal**). That second half closes a live bug — with no lens in the developer's config, debug mode solved at 10.20°, self-heal matched it to the hq's 25 mm within 1.3%, and wrote a real lens into the config off frames from a filesystem. Attach a real camera afterwards and the now-stated 25 mm stops it solving, and self-heal cannot undo it, because it only ever writes into an absence.

`CameraInterface.optical_train_known()` defaults **True**, so a camera backend has to opt *out* — a new hardware backend inherits the gate rather than silently losing it. Only the debug camera opts out.

## Documentation

This release is mostly documentation, and it is a substantial rewrite rather than a tidy-up.

### The manual is now in simplified technical English (#585, #586–#600)

Every user-facing page has been converted to a consistent house style built for this specific audience: readers standing outdoors in the dark, reading on a phone, often working through the English manual as a second language because the interface ships in German, Spanish, French and Chinese.

Seven rules: one idea per sentence, active voice, imperative instructions, simple tenses, no auxiliary chains, at most three stacked nouns, and one word per concept. The approved-term table is evidence-based — a sweep of the 13 user-facing pages counted the existing usage and the majority won (`select` over choose/pick, `screen` over display, `press` over push/tap, `object` over target/DSO, `telescope` over scope).

Pages converted: catalogs, equipment, software, v2.5 upgrade, SkySafari, connectivity, SD card, troubleshooting, menu map, quick start, the user guide, the build guide, and the shared camera includes. The starting point was 259 em-dashes and 83 semicolons across the manual.

The ring-shaped shortcut menu is now called the **Quick Menu** everywhere in the manual (#607). Polar alignment was the one section still calling it the marking menu, which is the internal code term — a reader who meets both names reasonably wonders whether they are two different things.

### New: Sky Quality Meter page (#606)

The SQM was rebuilt across #532, #544 and #560, all of which shipped in v2.6.1, but the manual never followed. Worse, the menu map still told users that "a recent solve gives the most reliable value" — which describes the pre-2.6.1 stellar path. The published value has been radiometric and solve-independent since 2.6.1, and deliberately keeps updating *through* failed solves and cloudy frames.

The new `docs/source/sqm.rst` covers reading the screen, why no plate solve is needed, why the value is not altitude-corrected, the Bortle bands (taken from the table the code actually uses rather than approximated), and the calibration wizard: when you need it, which is normally never.

It is honest about what calibration does, because the code does not support overselling it — the dark-current rate is the lasting contribution, the bias offset is superseded by the in-session black-level tracker, and read noise is diagnostic only. The headline archive accuracy figures were measured with no calibration file present at all.

### Corrections from support (#604)

Worked through a support-driven review of every page, verified against source rather than carried over on trust:

- **Equatorial platforms** (the most consequential): an alt-az telescope on an EQ tracking platform is still *operated* in alt-az. The docs told those owners to set Mount Type to Equatorial.
- **Getting a GPS lock** — a new section covering the ephemeris download, why `Sats seen/used 0/0` is not a progress bar, why power cycling restarts the wait, and why a phone is not a fair comparison. Plus a "The GPS never locks" troubleshooting symptom.
- **Rev4 Straight** sits at 45°, not "straight back". The old wording argued rear-focus telescope owners out of the configuration that actually suits them.
- **Comets and Planets** added to the catalogs page, both needing a GPS lock, with the practical "power up on WiFi beforehand" advice for comet element refresh.
- **Sleep mode** — only key presses hold the PiFinder awake. Motion wakes it but does not reset the timer, which is why polar alignment and slow slews dim the screen mid-task.
- **Eyepiece AFOV must be a whole number** — a decimal silently discards the eyepiece while still reporting "Eyepiece added".
- Smaller fixes: SkySafari's floor stated once (a paid version, 6 or later), the dovetail is one M5 bolt and does not require removing the PiFinder, field temperature reports run to 45 °C / 110 °F, Test Mode surfaced in the FAQ as the cloudy-night answer, and the web nav label reads "Network Setup" in both places.

## Known Sharp Edges

- **A mis-stated lens still means no solves, and the device deliberately does not recover from it.** Self-heal writes into an *absence*, never over a statement, so it does not rescue you here: the gate is centred on what you declared, and a wrong declaration puts every frame outside it. The failure presents as an exposure problem, because auto-exposure is driven by match count rather than centroid count. The log now names which case you are in — `Optical train: stated 16mm lens on imx462, …` versus `assumed` — so it tells you both what the device thinks is fitted and whether anybody told it that.
- **Changing the physical lens after self-heal deadlocks, exactly as it does for any stated lens.** Once the device has measured its lens it has *stated* one, so swapping the glass leaves the gate tight around the old lens, no frame solves, no measurement arrives to correct it, and you must set the menu by hand. This is 2.6.2's accepted consequence, but it newly reaches people who never opened the Lens menu — before this change they had a window wide enough to absorb the swap. The general cure is to re-open the gate on sustained zero matches *with adequate centroids*, which is #611's scope. Until then it is documented in `troubleshooting.rst`.
- **Switching Camera Type in the menu does not clear the stored lens.** The sensor is re-detected on every boot; the lens is a sticky setting nothing invalidates. So if you have explicitly chosen a lens and then swap camera types — for example a v3 user moving to the v2 HQ camera, which ships with a different lens — the device carries your old declaration onto the new sensor and stops solving. Re-select the correct lens after any Camera Type change.
- **The 25 mm lens on an imx296 or imx462 cannot solve at all**, even when correctly declared. Those trains derive 8.26° and 6.26°, and the shipped pattern database is built for `[10°, 30°]`. The solver logs an explicit error when a gate falls entirely outside the database range, but the menu still offers the combination. These are not shipped configurations — the 25 mm exists for the HQ camera — but the menu does not say so.
- **The 12 mm lens is only partly calibrated** (#612). Its effective focal length is now measured — 13.04 mm, from six solves on a rev4 imx462 fitting 12.4366 ± 0.0025°, cross-checked by putting the 16 mm on the same board and reproducing that lens's derived field to 0.02%. The other two values are still assumptions: `radiometric_zero_point` is calibrated per sensor *on the shipped lens*, so a 12 mm user currently gets the 16 mm's zero point, and the f-number is a conservative f/2.0 against a plausible f/1.6–f/2.0. One referenced exposure sweep closes both.
- **The 12 mm's 13.04 mm rests on a single sample.** The 16 mm earned its 15.61 mm by reproducing two independently calibrated field widths on two different sensors. The 12 mm has been measured once, on a rev4 imx462, with the 16 mm fitted to the same board on the same night as the control. A second sample — ideally on an imx296, so the sensor half varies too — would put it on the same footing. Recorded as an amendment to ADR 0029 rather than a rewrite, because only the arithmetic moved: the regression 0029 exists to fix was real under either constant.
- **A Nearby list stops at the 200 nearest objects.** Scrolling no longer reaches anything beyond that, and there is no indication on screen that the list has been cut. Extending the window lazily as you scroll past 200 was considered and rejected: it buys back an ordering with no observing use, at the price of carrying a paging state machine through the re-rank path. Use the Catalog or RA sort to reach the full set.
- **The RA sort works but cannot be selected.** `SortOrder.RA` now sorts, and its label is drawn correctly wherever it appears, but the Quick Menu's Sort submenu still offers only Nearest and Standard — the slot RA would occupy is an empty option. Nothing regressed here; the sort was previously unreachable *and* unimplemented, and is now unreachable and implemented.
- **Leaving the Focus screen sideways can still leave the exposure held, which turns auto-exposure off for the rest of the session.** `MenuManager.add_to_stack` only calls `inactive()` on the outgoing screen when the *incoming* one is stateful, and `key_long_left` only deactivates the top of the stack — so anything pushed over Focus buries it, and going long-LEFT home from there discards it without releasing the hold. Removing the Quick Menu Exposure jump took away the route you were most likely to take, but three remain: long-RIGHT to object details, the power button, and an incoming object push from SkySafari — and that last one you do not initiate at all. The camera then stays at a fixed manual exposure and zero-match recovery stops running, while Settings → Camera Exp still shows "Auto". Re-selecting Auto, or a reboot, restores it. Backing out of Focus with LEFT — the ordinary route — is unaffected. The SQM screen and daytime align share the same underlying lifecycle gap. Fixing it centrally is not safe, because the date, time and location entry screens fire commit callbacks from `inactive()` and would commit early whenever a child screen is pushed — the asymmetry is load-bearing, not an oversight.
- **The center-object readout shows catalog designations, not popular names.** M 45 reads "M 45 Cr 42", not "Pleiades" — the catalog has no "Pleiades" entry at all, and the readout takes the first cross-designation exactly as the object lists already do. Preferring a popular name would be a change to that shared convention, not a fix in the readout.
- **The Stellarium dialect is verified at the protocol level, not yet broadly on hardware.** The push path was reverse-engineered against Stellarium Mobile Plus and every reply is covered by the new `test_pos_server.py` suite, but a live-app session against current Stellarium desktop and Mobile Plus is a test-plan gate, not something this release has already banked. SkySafari's traffic is covered by the same suite and its behaviour was deliberately left byte-compatible.
